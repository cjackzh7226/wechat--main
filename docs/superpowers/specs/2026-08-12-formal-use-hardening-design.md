## 1. 背景与目标

程序即将投入个人正式使用。当前通过 `启动.bat` 启动，源码运行数据、历史 EXE 数据和正式 AppData 数据存在分离风险；自动发送链路还存在聊天对象识别、并发、去重、发送确认、知识库冲突和持久化完整性等安全问题。

本次采用“分阶段安全加固”方案，不做整套重写。目标是：

1. 自动回复只能发送知识库内已有答案，禁止自由生成、改写或联网补答。
2. 同一问题按“社团 / 民非”硬分区，不能跨类型误用答案。
3. 确实没有可靠答案时，自动发送精确文本 `暂未查到对应答案`。
4. OCR、聊天身份、窗口状态或发送状态异常时不发送，避免错发和重复发送。
5. 源码版和 EXE 版统一使用一份正式数据。
6. 交付可直接双击启动的目录式 `聊小智.exe`，不再以批处理文件作为正式入口。
7. 建立可复现的自动测试、企业微信真人测试、打包校验、回退和运维日志流程。

## 3. 核心业务边界

### 3.1 唯一允许的回复来源

正式自动发送链路只允许：

1. 在本地知识库中召回候选记录；
2. 由大模型对候选做排序和一致性判断；
3. 按选中的 `record_id` 从知识库重新读取原始答案；
4. 校验答案哈希后原样发送。

禁止：

- 让大模型生成或改写答案；
- 根据常识补写答案；
- 联网搜索后回答；
- 使用本地预设规则临时拼接答案；
- 从大模型输出中直接提取答案正文；
- 由隐藏配置重新开启旧的自由生成模式。

### 3.2 兜底与技术失败的区别

- 业务上没有合格知识库答案：自动发送 `暂未查到对应答案`。
- OCR 失败、聊天对象无法确认、窗口发生切换、程序检测到用户正在输入、发送结果不确定、数据损坏或其他技术异常：不发送，记录异常并等待安全重试或人工处理。

技术异常不能伪装成“没有知识库答案”，否则可能将兜底文本错发给错误联系人。

## 4. 自动发送安全状态机

所有单聊和群聊共用一条串行状态机：

```text
等待新消息
  -> 稳定识别
  -> 知识库匹配
  -> 大模型判断
  -> 发送前复核
  -> 执行发送
  -> 发送结果验证
  -> 写入发送账本
```

同一时刻只允许一个识别、匹配和发送任务进入关键区，禁止单聊线程、群聊线程和自动切换线程并行操作企业微信。

### 4.1 单实例

使用 Windows 单实例锁。重复启动时不创建第二个监控和发送实例，而是唤醒或提示已有程序。源码版、旧 EXE 和新版 EXE 也必须竞争同一个正式实例锁。

### 4.2 启动基线

程序启动后先记录当前可见消息作为基线，不回复启动前已经存在的旧消息。发送账本在重启后继续生效。

### 4.3 聊天身份

聊天身份至少由以下信息共同确定：

- 企业微信主窗口标识；
- 标准化后的顶部聊天名称；
- 聊天类型：单聊或群聊。

不能只使用主窗口标题或窗口句柄，因为不同联系人共享同一个企业微信窗口。

### 4.4 手动切换

检测到用户手动切换聊天后保留稳定等待，但等待结束后必须重新读取并核对：

- 顶部聊天名称；
- 聊天类型；
- 最新消息；
- 当前客户消息是否仍是待处理消息。

企业微信不在前台、用户正在操作或输入、聊天身份不稳定时，不截图抢焦点，也不发送。

### 4.5 发送前复核

发送前必须重新读取聊天身份和最新消息。OCR 读取失败时禁止用缓存内容代替本次复核结果。

如果聊天名称、聊天类型、最新消息或客户轮次与生成候选时不一致，则取消本次发送并回到等待状态。

### 4.6 发送结果验证

按键或粘贴成功不等于消息已发送。发送后通过 OCR/界面状态确认出现了本方新气泡：

- 明确验证成功：记录为已发送；
- 明确没有发送：只允许安全重试一次；
- 状态不确定：不自动重试，记录告警，避免重复发送。

### 4.7 去重

- 单聊：以“聊天身份 + 当前客户轮次”作为持久化去重键。
- 群聊：以“群名 + 发送人 + 消息指纹”作为去重键。
- 只有发送验证成功后才标记完成。
- 预处理、匹配或发送失败不能提前吞掉消息。

## 5. 知识库数据模型与机构分区

每条正式知识库记录至少包含：

- `record_id`
- 问题原文
- 答案原文
- `org_scope`：`social`、`mfei`、`both` 或 `unknown`
- 关键词
- 来源文件和来源定位
- 来源哈希
- 答案哈希
- 状态：启用、冲突、待确认或停用

### 5.1 机构类型判定顺序

1. 当前问题中的明确机构类型表达；
2. 最近聊天上下文中最近一次明确的机构类型表达；
3. 仍无法确定时，只允许使用 `both` 记录，或社团和民非答案完全一致的记录；
4. 类型不明且两个分区答案不同，发送 `暂未查到对应答案`。

机构分区是本地硬规则，大模型无权跨分区选择。

### 5.2 当前 449 条数据的迁移基线

初步分类结果：

- `unknown`：248 条
- `social`：82 条
- `mfei`：68 条
- `both`：51 条

在机构分区后，仍有 17 组同分区、相同问题但答案不同的冲突，共涉及 36 条记录。

迁移原则：

- 只合并“标准化问题、机构类型和标准化答案均相同”的完全重复项；
- 跨机构类型的不同答案完整保留；
- 17 组同分区冲突完整保留但标记为禁止自动发送；
- 生成冲突清单，供后续人工确认；
- 冲突未解决前命中该问题时发送 `暂未查到对应答案`；
- 保留迁移前归档备份，不能通过覆盖方式丢失原记录。

## 6. 候选召回与大模型判断

### 6.1 本地召回

先完成机构分区，再在合格分区中本地召回。排除：

- 状态为冲突、待确认或停用的记录；
- 机构类型不符的记录；
- 缺少必要问题、答案或关键来源信息的记录。

合格候选最多选取 1 至 3 条交给大模型。现有本地置信阈值 30、领先差值 8 暂时保留；只有在 449 条知识库回归结果支持时才能调整。

### 6.2 大模型返回协议

大模型只能返回严格 JSON：

```json
{"chosen": 1, "consistent": true}
```

校验规则：

- `consistent` 必须是 JSON 布尔值，字符串 `"false"` 不能转成真；
- `chosen` 必须是合法整数候选编号；
- 围栏代码、解释文字、越界编号、缺失字段或类型错误均视为失败；
- 超时、无密钥、接口错误、解析失败或判断不一致时发送 `暂未查到对应答案`；
- 客户问题和候选文本按不可信输入隔离，不能改变系统权限边界；
- 即使模型受到提示注入，本地机构分区、记录状态和哈希校验仍是最终权威。

## 7. 知识导入

### 7.1 结构化文件

Excel、CSV 等结构化文件直接读取问题和答案，保持答案原文。只有字段识别确实需要时才允许模型协助识别列，模型不能修改单元格答案。

### 7.2 非结构化文件

PDF、Word 等非结构化文件中，模型提取的问答必须关联可核查的来源位置。无法映射回来源原文的答案只能进入待确认区，不能直接启用。

### 7.3 长文本

长文本保持完整，不强制分块。如果超过模型或接口的输入上限，则终止该文件导入并明确报错；禁止静默截断、擅自分割或保存残缺结果。

### 7.4 导入事务

- 导入写入临时暂存区；
- 支持检查点和明确失败报告；
- 激活前生成重复、冲突和来源完整性报告；
- 全部校验通过后原子切换；
- 部分失败不能破坏正式知识库；
- 取消超过 3,000 条后静默丢弃旧记录的行为。

## 8. 正式数据迁移与持久化

### 8.1 唯一数据目录

源码版和 EXE 版统一使用：

`%APPDATA%\WeChatStyleReplyAssistant\`

程序安装目录不保存用户知识库、聊天状态和 API 密钥。

### 8.2 首次迁移

- 迁移现有 v4 `user_data` 中的 449 条记录；
- 当前正式 AppData 中的 3 条旧记录直接删除，不与 449 条数据合并；
- 迁移前后的记录数量、状态和哈希必须核对；
- 生成迁移报告；
- 迁移成功后才切换正式数据；
- 失败时保留旧数据，禁止留下半迁移状态。

### 8.3 原子写入与恢复

重要数据采用“临时文件 -> 结构校验 -> 刷盘 -> 原子替换”的写入流程，并保留最近 5 个有效版本。

正式文件损坏时：

1. 自动尝试最近的有效备份；
2. 恢复成功后明确提示；
3. 所有备份均无效时关闭自动发送；
4. 禁止创建空文件覆盖损坏数据。

知识库和向量索引不一致时，以知识库正文为准重建索引。

### 8.4 配置校验

- 配置文件带模式版本；
- 布尔值只接受真正的布尔类型；
- 时间间隔、阈值和聊天区域有明确上下限；
- 非法关键配置会关闭自动发送；
- 旧版本配置通过显式迁移升级；
- 未知或隐藏字段不能启用自由生成模式。

### 8.5 API 密钥

API 密钥使用 Windows 当前账户加密保护，`settings.json` 只保留引用或配置状态。日志、诊断包和打包文件不得包含明文密钥。

## 9. 发送账本与日志

### 9.1 发送账本

持久化记录：

- 脱敏聊天身份；
- 聊天类型；
- 客户消息指纹；
- 知识库 `record_id`；
- 状态：准备、已按键、已验证、状态不确定或失败；
- 时间和失败原因。

### 9.2 运行日志

运行日志位于 AppData 独立目录，按日期和大小轮换并限制总空间。默认只记录脱敏身份、匹配分数、记录编号、机构判定依据、模型判断、发送前复核和发送验证结果。

默认不完整记录客户消息、答案正文和联系人昵称。一次性调试日志必须由用户主动开启，结束后自动关闭。

### 9.3 项目开发日志

本次及后续运维、测试和打包工作按实际日期追加至 `.workbuddy\memory\YYYY-MM-DD.md`，至少记录：

- 修改文件和原因；
- 测试命令与结果；
- 数据迁移数量及校验；
- 打包版本与哈希；
- 备份位置；
- 遗留风险和回退方法。

## 10. 测试设计

### 10.1 自动化测试

保留现有 297 项测试并增加以下覆盖：

- 机构硬分区和上下文判定；
- 17 组冲突不得自动发送；
- 大模型不能生成或改写答案；
- 字符串 `"false"` 不能被误判为真；
- 无合格答案时发送精确兜底文本；
- OCR、身份或发送状态异常时不发送；
- 手动切换、窗口后台、用户输入；
- 重启防重；
- 群聊按群名、发送人和消息去重；
- 配置损坏、知识库损坏和索引错位恢复；
- API 超时、断网、密钥失效和异常 JSON；
- 快速连续消息、长消息、空消息和特殊字符；
- 多实例拦截。

所有自动测试使用隔离的 AppData、临时目录、日志和缓存，不能触碰正式运行数据。

### 10.2 知识库专项检查

输出机器可读报告和中文摘要，覆盖：

- 总数及内容哈希；
- 各机构类型数量；
- 完全重复项；
- 跨机构合法差异；
- 同机构冲突；
- 缺失来源、问题或答案；
- 启用记录召回情况；
- 冲突和未确认记录拦截情况。

### 10.3 企业微信真人测试

- 单聊：`- @微信`
- 暂定测试群：`-、阳光、琳、-`

顺序：

1. 观察模式只记录预期结果，不实际发送；
2. 核对聊天名称、类型和最新消息；
3. 单聊知识库命中；
4. 单聊无匹配兜底；
5. 手动快速切换防错发；
6. 企业微信后台不抢焦点、不发送；
7. 重启后不回复旧消息；
8. 群聊正确 @ 时回复；
9. 群聊未 @ 时不回复；
10. 不同群成员相同消息的去重；
11. 发送状态不确定时不自动重发。

真人测试必须核对企业微信中实际出现的本方气泡，不能只依据程序日志或按键动作判定成功。

## 11. 分阶段上线

1. 观察模式：只记录候选和预期发送内容；
2. 受控发送：仅对指定联系人和测试群开放；
3. 正式模式：验收通过后再开放其他聊天对象。

发现错聊天、重复发送、自由生成或机构类型串用时，立即关闭自动发送并回退到上一阶段。

## 12. EXE 打包与启动

正式交付采用目录式 EXE：

```text
聊小智\
├─ 聊小智.exe
├─ 程序依赖文件
└─ 版本及校验信息
```

用户直接双击 `聊小智.exe`，不显示命令行窗口。可创建桌面快捷方式。`启动.bat` 仅保留为开发诊断工具，不作为正式入口。

目录式 EXE 优先于单文件 EXE，原因是 OCR、图像识别和企业微信自动化依赖较多；目录式启动更快、临时解压风险更小，也更便于校验依赖完整性。

打包要求：

- 固定 Python、PyInstaller 和依赖版本；
- 明确包含 OpenCV、OCR 和企业微信校准文件；
- 排除密钥、知识库、聊天记录和用户配置；
- 生成版本号、构建时间、源码摘要和 SHA-256；
- 新版本使用独立版本目录，不覆盖上一可用版本；
- 新旧版本共用正式 AppData，但不能同时运行；
- 保留上一版本和数据备份作为回退依据。

## 13. 启动自检

EXE 启动时检查：

- 单实例锁；
- 正式数据目录读写；
- 知识库结构、数量和哈希；
- 冲突记录处于禁用状态；
- OCR、图像依赖和校准文件；
- 企业微信窗口状态；
- API 配置；
- 发送账本。

关键检查失败时保持自动发送关闭，并在界面直接显示原因。

只有全部满足以下条件才算完成：

1. 原有测试和新增测试全部通过；
2. 源代码编译检查通过；

7. 单聊和群聊真人测试通过；
8. 没有错聊天、重复发送和自由生成答案；

## 15. 实施约束

- 本项目不是 Git 仓库，因此设计文档和后续修改通过 ZIP、文件哈希、测试结果及日期日志形成可审计链，不执行 Git 提交。
- 实施顺序应先写测试和迁移校验，再修改业务代码；每个阶段完成后运行对应测试。
- 未通过观察模式和受控真人测试前，不开放全量自动发送。
- 任何实现细节若需要改变本设计的业务边界，必须先取得用户确认。
