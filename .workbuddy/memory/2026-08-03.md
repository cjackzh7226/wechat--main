## 新增实时搜索增强逻辑（解决大模型知识截止问题）

**背景**：用户反馈 DeepSeek 模型回答"蜘蛛侠电影出到几了"时仍答 2023 年的信息，原因是 LLM 训练数据有知识截止日期、且本项目定位是聊天回复助手（system prompt 禁止编造）。

**改动**：
- 新建 `web_search.py`：基于 DuckDuckGo HTML 搜索 + Bing 兜底（无需 API Key），含 should_search 事实性问题启发式、5 分钟内存缓存、搜索失败 60 秒熔断、format_search_context 结果格式化。requests 不可用时静默降级。
- `settings.py`：新增 `enable_web_search`（默认 True）和 `search_max_results`（默认 3，限制 1-6）。
- `reply_engine.py`：只在**实际生效的 `_readable_build_prompt`** 中注入搜索块（文件末尾会覆盖原 `_build_prompt`，改原版无效）；命中事实性问题时搜索并把摘要注入 prompt + 增加"以参考信息为准"规则。
- `float_ui.py`：设置弹窗"文本接口配置"区新增"实时搜索增强"复选框（TEXT 加 web_search/web_search_tip 文案），save() 和 choose_and_analyze_sop_training() 都写入该字段。

**注意事项**：
- reply_engine.py 里有新旧两套 `_build_prompt`/`_generate_with_current_model`/`_quality_filter`/`_refill_messages`，运行时以文件末尾的 `_readable_*` 覆盖为准，改逻辑必须改 readable 版本。
- float_ui.py 中 save() 与 choose_and_analyze_sop_training() 各有一份 settings 保存代码，加新字段要两处都改。
- 验证：should_search 9 组用例全过；蜘蛛侠搜索返回 2026 年最新档期信息；所有文件编译通过；test_core 无异常；设置字段往返读写正常。

## 排查"接口未生效"（追加）

**根因**：用户 settings.json（%APPDATA%\WeChatStyleReplyAssistant\settings.json）里实际是 zhipu 配置（provider=zhipu, model=glm-4-flash-250414），且该智谱 Key 实测 401"令牌已过期"。用户以为已改成 DeepSeek，但没保存成功（大概率设置弹窗改完没点"保存"直接关闭）。程序用失效 Key 请求 → last_error 非空 → 界面显示"接口未生效"。

**关键事实（2026-08 时点）**：DeepSeek 官方最新模型名为 `deepseek-v4-flash` / `deepseek-v4-pro`，`deepseek-chat`/`deepseek-reasoner` 已于 2026-07-24 弃用（兼容映射到 v4-flash 的非思考/思考模式）。base_url 仍为 https://api.deepseek.com。

**代码修复**：
- `llm_clients.py`：deepseek 预设 model 由 deepseek-chat 更新为 deepseek-v4-flash。
- `settings.py`：deepseek provider 下 deepseek-chat/deepseek-reasoner 自动升级为 deepseek-v4-flash。

**用户选择**：自己在 UI 里配置（已给出步骤：设置→文本接口配置→选 DeepSeek→填 Key→务必点保存）。后续若仍报错需看"接口提示"具体文案。

## 修复"DeepSeek 返回里没有识别到文本"（追加）

**根因（已复现实锤）**：deepseek-v4-flash 默认是**思考模式**，响应含 reasoning_content（推理过程）。程序 max_tokens=280 太小，prompt 长（多轮聊天+搜索摘要）时推理内容占满输出配额 → finish_reason=length、content 为空 → extract 提取不到 → 报"返回里没有识别到文本"。属偶发（实测 3 次中 1 次复现）。

**修复（llm_clients.py）**：
- `max_tokens`: 280 → 600
- thinking disabled 由仅 zhipu 扩展为 `{"zhipu", "deepseek"}`：`payload["thinking"] = {"type": "disabled"}`

**验证**：修复后 3 次超长场景 reasoning_len=0、content 均非空、finish=stop；端到端 generate 输出 3 条正确候选（9部真人+动画2部+2026新片），来源 DeepSeek API 调用1次，无错误。用户需重启程序生效（启动.bat / .venv python main.py）。

**注意**：DeepSeek 官方文档确认 v4-flash 即原 deepseek-chat 的升级（非思考/思考模式由 thinking 参数控制），v4-pro 为更强推理版。

## 修复"候选刷新但不发送"死循环 + 搜索可见性（追加）

**症状**：全托管模式下候选列表一直刷新但消息发不出去，状态栏显示"等待对方消息/发送前复核未通过"，每次 OCR 都认为对方消息未回复。

**已改**：
1. `main.py` `_managed_preflight_context`：发送前复核截图 `allow_screen_fallback=False` → **True**。根因：窗口直接捕获失败（遮挡/硬件加速黑图）时复核永远失败 → 永不发送 → 候选死循环。改为 True 后仍有 turn 相似度校验兜底，不会误发。
2. `main.py`：新增发送链路诊断日志 `_diag()`，写入 `%APPDATA%\WeChatStyleReplyAssistant\managed_send.log`，覆盖 _maybe_managed_send 各分支、preflight、send 结果，便于下次精确定位。
3. `reply_engine.py` + `main.py`：搜索状态可见性。ReplyEngine 新增 `last_search` 字段（"已联网检索(N条)"/"无需联网"/"联网搜索已关闭"/"联网检索无结果"），`_generated_status` 显示在状态栏，用户可确认搜索是否触发。

**验证**：编译通过；last_search 三态正确；test_core 无异常。用户需重启生效；若再复现，取 managed_send.log 末尾几十行定位拦截分支。

## 修复"搜到了但模型不敢答/数字被过滤"（追加）

**症状**：问"福建省社会团体成立至少需要几个发起人？"，程序回复"建议以福建省民政厅最新工作规程为准，我再帮您核实一下"，而豆包直接答"一般不少于5个"。

**排查发现两个问题**：
1. **搜索本身完全正常**（实测搜到福建民政厅官方文件 PDF 摘要："一般由5个及以上自然人或法人发起"）。问题在模型层和过滤层。
2. **根因（过滤层 bug）**：`_reply_invents_numeric_data` 只检查聊天记录 context 里的数字，搜索摘要里的数字（如 5）被误判为"模型编造数字"，含数字的候选被 `_quality_filter_with_numeric_guard` 过滤删除 → 只剩"以官方为准"这类保守候选。prompt 里"不能编造数字"指令也加剧模型保守。

**修复（reply_engine.py）**：
- `_readable_build_prompt`：搜索成功后记录 `self.last_search_numbers`（搜索摘要中的数字集合）。
- `_quality_filter_with_numeric_guard` / `_reply_invents_numeric_data`：新增 allowed_numbers 参数，搜索摘要中出现的数字不算编造。
- prompt 动态化：有搜索块时规则4放宽为"数字以参考信息为准可直接采用"；search_rule 引导"直接给明确结论含数字，参考信息不足给'通常/一般'表述，禁止'我再核实一下'式敷衍"；system prompt 与 `_refill_messages` 同步按有无搜索块切换数字策略。

**验证**：发起人问题 → 3 条候选含"福建省规定社会团体一般需5个及以上自然人或法人发起"（与豆包一致更精确）；"大概200多单"仍被过滤（保护未破坏）；test_core 通过。
