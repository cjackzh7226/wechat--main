# 2026-08-15 工作日志

## 本次问题

- 用户实测发现：企业微信与“聊小智”并排显示时，手动“识别当前聊天”偶尔要切换聊天后才识别；识别后又被空闲轮询覆盖成“等待聊天窗口”。
- 识别成功后，托管路径仍提示“企业微信不在前台”或“群聊发送前识别失败”，没有按“可见企业微信 OCR → 发送前安全切焦点 → 重新识别 → 发送”的预期工作。
- 工作区存在一份未提交的 `conversation_list.py` 回退，删除了顶部标题标定、外部群特征、精确系统白名单和新版 Pillow 像素兼容层，造成普通联系人/系统会话/群聊分类回归。

## 已完成修复

- 手动“识别当前聊天”在 off / observe / controlled / full 四种模式下一律只生成知识库候选预览，不进入后台托管 worker，不激活窗口、不写发送台账、不发送。
- 手动预览无知识命中时显示精确 `暂未查到对应答案`；技术故障、OCR 为空、群聊未完整 @ 当前账号分别显示明确的未发送状态。
- 空闲轮询不再覆盖已经识别的聊天、上下文、候选回复和状态。
- 新增严格窗口原语：原始前台 HWND、根 HWND、可见/非最小化窗口重验、精确目标激活并确认。
- observe 模式可对旁边可见但不在焦点的企业微信做 OCR，永不激活、永不发送。
- controlled / full 模式只在真正发送前处理焦点：
  - 企业微信已在前台：直接进入严格重识别；
  - “聊小智”在前台：只允许激活已排队的精确企业微信 HWND；
  - 用户正在操作其他程序：不抢焦点，本轮不发送；
  - 目标窗口无效、隐藏、最小化、激活失败：不发送。
- 激活后必须重新 OCR，并再次核对 HWND、平台、顶部聊天名、聊天类型、发送者和客户问题；任一变化都不写发送终态、不发送。
- 自动 sender 仍使用 `allow_activate=False`；焦点授权只存在于协调器的发送前边界。
- 恢复 `conversation_list.py` 的必要逻辑；修复前原文件已备份到忽略目录：
